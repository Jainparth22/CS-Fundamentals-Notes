# SQL: 25 Most-Asked Questions (with answers)

**Q1. WHERE vs HAVING?**
WHERE filters rows before grouping and cannot use aggregates; HAVING filters groups after aggregation.

**Q2. In what order is a query logically processed?**
FROM/JOIN, WHERE, GROUP BY, HAVING, SELECT (aliases are created here), DISTINCT, ORDER BY, LIMIT. That is why a SELECT alias cannot be used in WHERE.

**Q3. Explain the join types.**
INNER keeps matches only; LEFT keeps all left rows with NULLs when unmatched; RIGHT mirrors it; FULL OUTER keeps all rows from both; CROSS gives every combination; a self join joins a table to itself (employee to manager).

**Q4. Why does `col = NULL` never match, and how do you handle NULLs?**
NULL means unknown, so comparisons with it are unknown, not true. Use `IS NULL`, `COALESCE`, and be careful with `NOT IN` when the list contains NULL (prefer `NOT EXISTS`).

**Q5. `COUNT(*)` vs `COUNT(column)` vs `COUNT(DISTINCT column)`?**
All rows; non-NULL values in the column; distinct non-NULL values.

**Q6. UNION vs UNION ALL?**
UNION removes duplicates (extra sort/hash work); UNION ALL keeps them and is faster. Column count and types must match.

**Q7. DELETE vs TRUNCATE vs DROP?**
DELETE removes chosen rows (WHERE allowed, logged, triggers fire). TRUNCATE empties the table quickly and resets identity. DROP removes the table definition too.

**Q8. Primary key vs unique constraint?**
One primary key per table, no NULLs, identifies rows. A table can have many unique constraints and (in most engines) NULLs are allowed in them.

**Q9. What is a foreign key and what do the ON DELETE options mean?**
A column referencing another table's key to enforce referential integrity. CASCADE deletes children, SET NULL clears the reference, RESTRICT/NO ACTION blocks the delete.

**Q10. Subquery vs join vs CTE?**
A join combines tables directly; a subquery nests a query; a CTE (`WITH`) names an intermediate result for readability and reuse, and recursive CTEs walk hierarchies. Optimizers often treat them similarly.

**Q11. What is a correlated subquery and its cost?**
An inner query referencing the outer row, conceptually run per outer row. It can be slow; rewrite as a join or window function when possible.

**Q12. EXISTS vs IN?**
EXISTS stops at the first match and is NULL-safe; IN compares against a list/subquery result and misbehaves with NULLs in `NOT IN`. Prefer EXISTS for large correlated checks.

**Q13. Window function vs GROUP BY?**
GROUP BY collapses rows into one per group; a window function (`OVER (PARTITION BY ... ORDER BY ...)`) adds an aggregate or rank to each row without collapsing. You cannot filter on one in WHERE; wrap it in a subquery or CTE.

**Q14. ROW_NUMBER vs RANK vs DENSE_RANK?**
ROW_NUMBER is unique (1,2,3,4); RANK gives ties the same rank and skips (1,2,2,4); DENSE_RANK gives ties the same rank without gaps (1,2,2,3).

**Q15. What do LAG and LEAD do?**
They read a value from the previous or next row in the window order (e.g. day-over-day change, time between events).

**Q16. How do you compute a running total?**
`SUM(amount) OVER (PARTITION BY customer ORDER BY created_at)`; with a frame `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` for exactness.

**Q17. How do you find the second or Nth highest salary?**
`DENSE_RANK() OVER (ORDER BY salary DESC)` and filter `= N`, or `SELECT DISTINCT salary ... ORDER BY salary DESC LIMIT 1 OFFSET N-1`; subquery with MAX for the second highest.

**Q18. How do you get the top N rows per group?**
Rank inside each group with `ROW_NUMBER()/DENSE_RANK() OVER (PARTITION BY group ORDER BY metric DESC)` in a CTE, then filter `rank <= N`.

**Q19. How do you find and delete duplicates?**
Find with `GROUP BY cols HAVING COUNT(*) > 1`. Delete by numbering rows per duplicate set with `ROW_NUMBER()` and removing those with number > 1 (or keep `MIN(id)`).

**Q20. What is an index and how does it work?**
A separate sorted structure (usually a B+ tree) that lets the database locate rows in O(log n) instead of scanning. It speeds reads and slows writes and uses space.

**Q21. Composite and covering indexes; why does column order matter?**
A composite index follows the leftmost-prefix rule: it helps filters on its first column(s) in order. A covering index contains all needed columns so the query is answered from the index alone.

**Q22. Why might the database ignore an index?**
Functions on the indexed column, leading wildcard `LIKE '%x'`, implicit type conversion, low selectivity, stale statistics, or an `OR` over different columns. Make predicates sargable (compare the raw column).

**Q23. How do you read an execution plan / optimise a slow query?**
Run `EXPLAIN (ANALYZE)`; look for full scans, bad row estimates, expensive joins, sorts. Add or fix indexes, select fewer columns, avoid N+1 queries, rewrite subqueries, update statistics, and paginate with keyset pagination.

**Q24. ACID, isolation levels and deadlocks?**
ACID: atomicity, consistency, isolation, durability. Isolation levels (read uncommitted, read committed, repeatable read, serializable) trade anomalies (dirty, non-repeatable, phantom reads) for concurrency. A deadlock is a circular lock wait; avoid with consistent lock order, short transactions and retries. Optimistic locking uses a version column; pessimistic uses `SELECT ... FOR UPDATE`.

**Q25. Normalization, denormalization and upserts?**
1NF atomic values, 2NF no partial dependencies, 3NF no transitive dependencies; denormalize deliberately for read performance. Upsert atomically with `INSERT ... ON CONFLICT DO UPDATE` (PostgreSQL/SQLite) or `ON DUPLICATE KEY UPDATE` (MySQL) rather than select-then-insert, which races.
